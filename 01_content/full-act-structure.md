版本：full act structure draft v0.1  
用途：作為 `README.md`、`game-design.md`、`game-architecture.md`、`act-2-content-plan.md` 之間的幕次總綱。  
限制：此文件只整理內容階段與施工邊界；已實作狀態以 README 與 runtime data 為準。若本文件的早期幕次語句與 README / handoff 不一致，以 README / `codex-handoff-short.md` 為準。

## 1. 文件定位

本文件負責定義《元素迷宮：邊境冒險者》的五幕制長期骨架，讓後續內容規劃有清楚的先後順序。

本文件承接：

- `README.md` 的 project-level SSOT。
- `01_content/game-design.md` 的 v1 MVP 垂直切片。
- `01_content/game-architecture.md` 的擴大版系統架構。
- `01_content/act-2-content-plan.md` 的第二幕第一輪內容計畫。

本文件不取代上述文件，也不直接定義 runtime data。若未來進入實作，仍需依照以下順序逐步確認：

```text
內容文件
→ schema 檢查
→ registry / unlock key 規劃
→ data 最小新增
→ validation
→ engine 最小支援
→ smoke test
→ README / 文件同步
```

## 2. 五幕制總覽

五幕制的目的不是一次規劃所有細節，而是避免後續內容提早混入 runtime，造成 data、engine 與文件漂移。

| 幕次 | 主要定位 | 目前狀態 | 核心成果 |
|---|---|---|---|
| 第一幕 | v1 MVP 垂直切片 | 已完成可玩版 | 建立核心循環與第二幕伏筆 |
| 第二幕 | 灰燼裂谷與元素迷宮擴張驗證 | 火系 demo 前置閉環已完成 | 驗證中期元素迷宮擴張流程 |
| 第三幕 | 轉職與第二元素路線成形 | 未規劃細節 | 讓角色成長從裝備準備進入職業分歧 |
| 第四幕 | 中後期複合系統整合 | 未規劃細節 | 統合多元素、任務鏈、Boss 對策與城鎮功能 |
| 第五幕 | 終局迷宮與最終 Boss 封版 | 未規劃細節 | 收束主線、封版核心玩法與最終驗收 |

---

## 3. 第一幕：v1 MVP 垂直切片，已完成

第一幕對應目前已完成的 v1 playable vertical slice。

已完成內容包含：

- 四個初始職業：劍士、法師、盜賊、牧師。
- 邊境城鎮艾爾姆與主要店鋪。
- 青苔洞窟與焦石礦坑。
- 基礎戰鬥、掉落、任務、商店、合成、魔法書與存檔。
- Boss：山寨頭目葛倫。
- 結尾伏筆：血跡地圖、火之印記碎片、第二幕元素迷宮預告。

第一幕的作用是證明核心循環成立：

```text
進入迷宮探索
→ 戰鬥
→ 取得素材、金幣、經驗
→ 回城整備
→ 商店、合成、工會、魔法書強化
→ 挑戰更高階迷宮
```

第一幕目前不應再被大幅擴張。若要修改第一幕，應優先修正 bug、文件漂移或 validation 缺口，而不是把第二幕內容塞回 v1。

## 4. 第二幕：灰燼裂谷與元素迷宮擴張驗證

第二幕第一輪以「灰燼裂谷」作為第一個中期內容擴張案例。

第二幕的目標不是一次新增全部元素迷宮，而是驗證一條可重複使用的擴張方法：

```text
血跡地圖解讀
→ 灰燼裂谷線索
→ 城鎮新增準備需求
→ 灰燼裂谷探索
→ 灰燼守衛 Boss
→ 燼印深窟與燼印鎮衛
→ 確認未完成的火之印記核心
```

第二幕應優先驗證：

- 新迷宮能否沿用或最小擴充現有 `DUNGEONS` 結構。
- 新素材是否有明確來源與消耗出口。
- 新怪物與 Boss 是否能被 validation 檢查。
- 新 unlock key 是否集中於 registry。
- 新任務鏈是否能避免 engine 中大量硬寫。
- 火抗、補給、技能與合成是否共同支撐攻略路線。

第二幕火系 demo 目前已完成的前置閉環：

- 已處理灰燼裂谷偵查版。
- 已新增一座迷宮的最小 data 前置：`dungeon_ash_ravine`。
- 已新增 3 個普通怪與 3 個素材。
- 完成 `quest_boss_glen` 後會解鎖 `second_act_preview`、`unlock_act_2`、`unlock_ash_ravine`。
- 已新增最小偵查任務 `quest_ash_ravine_scout`。
- 灰燼裂谷已調整為 18 步入口偵查版。
- Act 2 Entry Balance & Guidance Patch 已完成，集中藥袋 special 裝備語意 bug 也已修正。
- 灰燼裂谷 Boss `boss_ash_guardian` 已完成，擊敗後取得第 2 枚 `key_fire_mark_shard`。
- 燼印深窟 `dungeon_cinder_seal_depths` 已完成，並加入 `boss_cinder_seal_sentinel`「燼印鎮衛」。
- 擊敗燼印鎮衛後取得第 3 枚 `key_fire_mark_shard`。
- 三碎片後工會詢問、神殿接橋與教會查閱結果已完成；三枚碎片被確認為「未完成的火之印記核心」。

第二幕後續仍應維持小切片：

- 不加入完整 Boss 階段制。
- 不處理 Element Decay。
- 不正式開放轉職。
- 不建立第二個元素迷宮。
- 不在同一輪加入完整火之印記、火印熔爐、火印守護 Boss、正式聖物、正式轉職、完整任務鏈或神殿正式流程。
- 目前沒有已批准的下一個 runtime 施工目標；若未來繼續，需先做單一小切片 read-only 邊界確認。

## 5. 第三幕：轉職與第二元素路線成形

第三幕應在第二幕第一輪完成驗證後才開始規劃。

第三幕的核心定位是讓玩家從「根據迷宮準備裝備與技能」進入「定義自己的角色玩法」。

第三幕未來可能承接：

- 未完成的火之印記核心。
- 神殿試煉入口預告。
- 第二元素印記路線。
- 第一批轉職條件。
- 職業分歧後的戰鬥定位。

第三幕可以開始處理：

- 第一批轉職路線的正式條件。
- 第二元素迷宮的主線定位。
- 職業專屬技能循環。
- 轉職試煉或鏡像試煉的第一版規格。

第三幕不應在第二幕尚未驗證前提前施工。特別是轉職、技能樹、第二元素互動與大型任務鏈，應先等灰燼裂谷流程證明可維護後再展開。

---

## 6. 第四幕：中後期複合系統整合

第四幕是多系統整合階段，不是新增單一迷宮或單一職業功能。

第四幕應在以下條件大致成立後才規劃：

- 至少一條第二幕元素路線完成。
- 第三幕已確認轉職或職業分歧的基本模式。
- validation 已能穩定檢查新增迷宮、任務、配方、怪物與 unlock key。
- engine 不再因每個新 Boss 或任務都需要大量硬寫。

第四幕可以整合：

- 多元素迷宮的互相對策。
- 中後期 Boss 的準備度檢查。
- 城鎮新功能，例如情報、鍊金、訓練或委託板。
- 多段任務鏈。
- 高階合成與稀有素材出口。
- 更完整的轉職成果。

第四幕不應提前導入，因為它依賴前幾幕建立好的資料治理與 engine 支援。

---

## 7. 第五幕：終局迷宮與最終 Boss 封版

第五幕是主線收束與封版階段。

第五幕應處理：

- 終局迷宮。
- 最終 Boss。
- 主要伏筆回收。
- 職業成長與元素印記的最終驗收。
- 封版前的平衡、validation 與 smoke test 覆蓋。
- README 與內容文件的狀態同步。

第五幕不應在前面幕次尚未穩定時提前設計細節。終局迷宮與最終 Boss 需要建立在完整的玩家成長、元素準備、任務推進與資料驗證之上。

第五幕的成功標準不是內容最多，而是讓整個專案能形成可交付的完整體驗。

## 10. Codex 施工邊界

在使用本文件進行 Codex 任務時，應遵守以下邊界。

允許：

- 閱讀本文件與相關 SSOT。
- 進行幕次定位、切片評估與文件一致性檢查。
- 在使用者明確要求時，新增或修改 `01_content/` 內的規劃文件。
- 提出 schema、registry、validation、engine 的最小修改理由與範圍。

不允許，除非使用者明確要求：

- 修改 `README.md`。
- 修改 `game-design.md`、`game-architecture.md` 或 `act-2-content-plan.md`。
- 修改 `02_schema/`。
- 修改 `03_engine/engine/game.py`。
- 修改 `04_data/data/`。
- 修改 `04_data/data/registry.py`。
- 修改 `06_tools/validate_data.py`。
- 新增 `act-3-content-plan.md`。
- 實作未批准的第二幕 runtime 內容；已完成的灰燼裂谷偵查版不代表可直接擴成完整第二幕。
- 處理 Element Decay。

每一輪 Codex 施工都應先確認本輪屬於哪一幕、哪一個最小切片，以及哪些檔案被允許修改。若任務只是文件規劃，應停留在文件層，不把候選內容推進 runtime。
