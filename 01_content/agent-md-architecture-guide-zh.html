協作文件架構／中文速覽

AGENTS.md 不該是百科；它該是一個讓 agent 能果斷開始、也知道何時停下來的入口。

文件變長是自然結果：agent 越能自主，團隊越想把經驗、例外與交接寫下來。問題不在「長」，而在於把不同用途的內容全塞進每次必讀的主檔。

我的看法：AGENTS.md 越來越像 agent 間的通訊協定與導航層，這是好事；但它不應承擔知識庫、進度日誌、完整流程手冊三種角色。把它們拆開，才能同時保有自主性與可判讀性。

推薦結構：一個短入口，三種按需閱讀的文件

每次必讀・約 300–700 英文字

AGENTS.md

任務邊界、預設自主權、硬紅線、如何找到下一層文件。它回答：「我現在可不可以動手？什麼時候必須停？」

↓ 任務需要時才讀
領域規範

子目錄 AGENTS.md／SKILL.md

例如 GUI、資料、部署、內容編輯。只在進入該區域時載入。

當前狀態

README／handoff／progress

目前完成到哪、已知問題、下一步；會過期的資訊放這裡。

↓ 需要證據或細節才讀
長期知識

設計文件、架構決策、測試、程式碼

理由、歷史、完整規格與可執行事實。這些不應重複濃縮進主檔。

你可以用這三個問題判讀任何一條 AGENTS.md 規則

1. 它是否改變預設行為？

「不要動 save 資料」會；「某功能目前完成 70%」通常不會。前者留主檔，後者移進進度文件。

2. 每個任務都需要它嗎？

不是的話，移到子目錄文件或技能文件，讓 agent 按任務載入。

3. 是否能被更短的原則取代？

一條「可回復、局部、可驗證的變更可自主進行」往往可取代十條工具或檔案例外。

警訊：它只是在描述歷史

版本流水帳、舊決策的逐字辯論、已完成清單，都會增加閱讀成本卻不提高當下決策品質。

一份足夠短、但不會讓 agent 過度保守的主檔核心

## Autonomy and safety

- Make routine technical decisions from repository conventions, tests, prior
  implementations, and authoritative documentation; do not ask users to decide
  what can be reasonably inferred.

- Proceed autonomously with scoped, reversible, and verifiable work. Preserve
  unrelated changes, run relevant checks, and reassess if evidence contradicts
  the approach or scope expands materially.

- Ask only when product intent, unavailable information, external authorization,
  irreversible/destructive actions, meaningful cost, security, or permission
  risk requires a decision.

- Require confirmation before production deployment, external messages,
  purchases, credential/permission changes, or destructive actions outside
  clearly approved targets.

其餘內容以連結指向各自的真實來源，而不是在此複製一份。

主檔變長時的「減肥」清單

□
留在 AGENTS.md：跨領域硬邊界、預設授權、文件入口、不可逆動作規則。
□
移到子目錄規範：只有 GUI、資料、部署或特定工具才需要的工作流。
□
移到進度／交接文件：目前階段、螢幕清單、已知 bug、下一步與舊決策。
□
移到測試／程式碼：能自動檢查的約束不應只靠自然語言記住。
□
定期刪除：已被更好規則涵蓋、已失效、或 agent 違反它也不會造成明顯問題的文字。

一個重要的心法：給自主權，不是給無限制授權

你不需要靠加長文件來讓 agent 膽大。真正讓 agent 能穩定前進的是明確的預設：在「範圍小、可回復、可驗證」內自行處理；碰到產品意圖、不可逆風險與外部副作用才停下。這樣未來模型能力提升，它會先把更多事情做好，而不會把更多事情擴張到失控。

建議把這頁當作維護 AGENTS.md 的審稿尺，而不是再加進 AGENTS.md 的內容。
